## Standard fixes

### dist/tests/slc_tarball_test.sh

#### [CONTEXTLESS_ERROR] New hard dependency on `jq` has no named guard, so a missing `jq` is reported as an artifact schema failure
- Location: line 518 (`jq -r '.language_definitions[0].udf_client_path.executable'`), guard block at lines 633-634
- Issue: the rewritten `slc_tarball_language_definitions_well_formed` now depends on `jq` both directly (line 518) and through the delegated contract script, but the runner guards only `readelf` (line 634). With `jq` absent, the delegated call exits 2 with `ERROR: jq not found — install jq` and line 507's `if ! shape_output=...` reports it as `slc_tarball_language_definitions_well_formed: shape check on <path> failed`, i.e. the run blames the artifact's metadata shape for a missing host tool. This is also the only realistic exit-2 path out of the child, so a named guard closes it entirely.
- Fix: In dist/tests/slc_tarball_test.sh, add `command -v jq >/dev/null 2>&1 || die "jq not found — install jq"` immediately after the existing `command -v readelf ... || die "readelf not found — install binutils"` line in the runner section, matching that guard's style, so a missing `jq` stops the run with its own named error before any assertion runs.

## Expert fixes

### dist/tests/language_definitions_fixtures_test.sh

#### [BROAD_CATCH] `assert_rejected` accepts any non-zero exit, so a harness error or an unrelated assertion counts as proof
- Location: lines 42-51 (`assert_rejected`), lines 53-62 (`assert_accepted`)
- Issue: `assert_rejected` asserts only `if bash "$CONTRACT_SCRIPT" "$path" >/dev/null 2>&1`, discarding both the exit code's meaning and the output. `language_definitions_test.sh` deliberately separates exit 2 (usage error, missing file, missing `jq` — lines 30-38) from exit 1 (contract violation), and the driver throws that distinction away. Two consequences, both silent: (1) with `jq` absent, or after any edit that makes the contract script die at startup, all five negative cases report `PASS` and only `language_definitions_accepts_conforming` fails — five assertions passing while nothing was checked; (2) a fixture rejected for a reason unrelated to the fact it varies still passes. Case (2) is live today: `root_key_renamed.json` produces three `FAIL:` lines (verified run), and the driver cannot tell the intended one from the two collateral ones. This is the same "failures share one cause, so they are not independent evidence" trap plan.md § Implementation Tasks task 1 calls out for the unmodified document, reproduced inside the driver that was supposed to close it.
- Fix: In dist/tests/language_definitions_fixtures_test.sh, give `assert_rejected` a third parameter `expected_message` and rewrite it to capture the child's behavior instead of only its truthiness: declare `local name="$1" fixture="$2" expected_message="$3"` and `local path="$FIXTURES_DIR/$fixture" output status` on separate lines (never `local output="$(...)"`, which masks the child's status), then `output="$(bash "$CONTRACT_SCRIPT" "$path" 2>&1)"`, `status=$?`; `die "$name: contract script could not run on $fixture: $output"` when `status` is 2; `fail "$name: $fixture unexpectedly passed the contract script"` when `status` is 0; `fail` with the captured output when `status` is 1 but `$output` does not contain `FAIL:` followed by `$expected_message`; `pass "$name"` otherwise. Apply the same `status`-capture and `die`-on-2 to `assert_accepted`, keeping its existing `status != 0` failure. Pass these expected substrings at the call sites, each verified to appear in the current output: `root_key_renamed.json` → `still declares the old root key 'languages'`; `deprecation_removed.json` → `has no 'deprecation' key`; `arguments_readded.json` → `still declares the old 'arguments' key`; `parameters_retyped.json` → `.language_definitions[0].parameters is not`; `executable_changed.json` → `.language_definitions[0].udf_client_path.executable is not`. Then verify by running `bash dist/tests/language_definitions_fixtures_test.sh` (expect 6 `PASS:`, exit 0) and, as negative evidence, by temporarily passing a wrong `expected_message` for one fixture and confirming that case fails.

#### [UNTESTED_ERROR_PATH] Six of the contract script's eleven failure branches have no fixture, including one no fixture can reach
- Location: fixture set under dist/tests/fixtures/language_definitions/; uncovered branches in dist/tests/language_definitions_test.sh at lines 41, 53, 61, 65, 69, 88
- Issue: plan.md § Implementation Tasks task 2 states this fixture family "is the plan's only evidence that each assertion discriminates; without it, an assertion that can never fail looks as verified as one that works", and the spec delta's NEW scenario requires that "each required field's absence, removal, or re-typing MUST fail the check". Six branches have no such evidence: `.schema_version == 2` (line 41), `.language_definitions | type == "array"` (line 53), `.language_definitions | length == 1` (line 61), `.aliases == ["RUST"]` (line 65), `.protocol == "localzmq+protobuf"` (line 69), and `.deprecation == null` (line 88). Line 53 is not merely uncovered but unreachable through the current fixtures: `root_key_renamed.json` trips the `has("languages")` branch at line 49, which returns before line 53 — the verified run on that fixture prints `still declares the old root key 'languages'` and never line 54's message. Line 88 is likewise shadowed: `deprecation_removed.json` trips `has("deprecation")` at line 84, so no fixture ever exercises a `deprecation` key present with a non-null value, which is exactly the case plan.md task 1 singled out as the reason presence and value are asserted separately.
- Fix: In dist/tests/fixtures/language_definitions/, add six negative fixtures, each a byte-for-byte copy of `conforming.json` varying exactly one fact: `schema_version_wrong.json` (`"schema_version": 1`), `definitions_not_array.json` (`language_definitions` as a single object instead of a one-element array, with no `languages` key, so line 53 is reached), `two_definitions.json` (the definition object duplicated so `length` is 2), `aliases_changed.json` (`"aliases": ["rust"]`), `protocol_changed.json` (`"protocol": "localzmq+json"`), and `deprecation_non_null.json` (`"deprecation": "deprecated"`). Then add one driver case per fixture to dist/tests/language_definitions_fixtures_test.sh — `language_definitions_rejects_schema_version_wrong`, `_rejects_definitions_not_array`, `_rejects_two_definitions`, `_rejects_aliases_changed`, `_rejects_protocol_changed`, `_rejects_deprecation_non_null` — using the three-argument `assert_rejected` from the `[BROAD_CATCH]` finding in this file, each with the expected `FAIL:` substring for the branch it targets (`does not declare schema_version 2`, `has no root 'language_definitions' array`, `does not hold exactly one definition`, `.language_definitions[0].aliases is not`, `.language_definitions[0].protocol is not`, `.language_definitions[0].deprecation is not null`). Run `bash dist/tests/language_definitions_fixtures_test.sh` and show all twelve cases passing.

#### [SHRINKABLE] Six wrapper functions whose whole body is one call repeating their own name as a literal
- Location: lines 64-86 (wrapper definitions), lines 88-93 (call site)
- Issue: each of `language_definitions_rejects_root_key_renamed` … `language_definitions_accepts_conforming` is a one-line body calling `assert_rejected`/`assert_accepted` with its own name spelled again as a string argument. `/speq:design-philosophy` § Deep Modules names this shape directly ("a function whose entire body is a call to another function with the same arguments — merge it into whichever side actually holds logic"). Beyond the 23 wasted lines, the duplicated name literal can silently disagree with the function name, in which case the output labels a passing case with the wrong test name and nothing detects it. The names must stay visible in the `PASS:` output, which the argument already provides.
- Fix: In dist/tests/language_definitions_fixtures_test.sh, delete the six wrapper function definitions and replace the six bare invocations at the bottom with direct `assert_rejected` / `assert_accepted` calls carrying the same test names as their first argument — one call per line, forming a single fixture-to-name block — using the argument list established by the `[BROAD_CATCH]` finding in this file. Verify the run still prints one `PASS:` line per case under the same names.

### dist/tests/language_definitions_test.sh

#### [CONTEXTLESS_ERROR] A malformed document fails four assertions, none of which says the JSON is unparseable
- Location: lines 35-38 (guards), lines 107-110 (runner)
- Issue: every assertion swallows `jq`'s own diagnostics (`>/dev/null 2>&1`), so a document with a syntax error produces four unrelated messages, the first being `$DOC does not declare schema_version 2` — none stating the constraint actually violated. plan.md § Design § Context records that "neither malformed JSON" was the cause of issue #90, i.e. unparseable metadata is a failure mode a reader will actively suspect, and the tarball assertion that consumes this script is named `slc_tarball_language_definitions_well_formed` while nothing in the chain asserts well-formedness by name. A malformed document is a violation by the subject, not a harness problem, so it belongs on the `fail`/exit-1 path rather than with the `die` guards.
- Fix: In dist/tests/language_definitions_test.sh, add a `language_definitions_document_is_valid_json` assertion that `fail`s with `"language_definitions_document_is_valid_json: $DOC is not valid JSON"` when `jq empty "$DOC" >/dev/null 2>&1` is non-zero and `pass`es otherwise, call it first in the runner, and gate the four existing calls behind `if [[ "$failures" -eq 0 ]]; then … fi` so a malformed document reports exactly one accurate failure instead of four misattributed ones. Then add `dist/tests/fixtures/language_definitions/malformed.json` (`conforming.json` with a trailing comma after the definition object) and a `language_definitions_rejects_malformed` case in dist/tests/language_definitions_fixtures_test.sh expecting the substring `is not valid JSON`, using the three-argument `assert_rejected` from the `[BROAD_CATCH]` finding. Run both scripts and show the new assertion passing on `build_info/language_definitions.json` and firing on the new fixture.
