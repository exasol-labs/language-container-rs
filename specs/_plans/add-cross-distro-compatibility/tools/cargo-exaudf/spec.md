# Feature: cargo-exaudf

Provides the `cargo exasol-udf` developer CLI that scaffolds a Rust UDF crate and builds it into a glibc-dynamic cdylib `.so` — so authors never hand-manage the build target or ABI constants.

## Background

`cargo-exasol-udf` is a Cargo subcommand binary invoked as `cargo exasol-udf <subcommand>`. By default `build` runs a plain host `cargo build --release`, producing a glibc-dynamic cdylib at `target/release/lib<crate>.so`; an optional `--target <triple>` flag overrides the build target for a native build on that host. The CLI performs no network I/O. The scaffold generated by `new` models the scalar RETURNS value-return channel.

A host build binds the artifact to two properties of the author's machine: the glibc the linker stamps symbol versions from, and the `rustc --version` string the SDK bakes into the vtable fingerprint. The SLC accepts an artifact only when the first is at or below its recorded glibc floor and the second equals its recorded builder rustc identity. Those two values are container facts, published as one committed builder record specified in `container/slc-platform-contract`. A host that satisfies neither has no host build path to a loadable artifact, so `build --container` runs the same release build inside the SLC's own builder image and takes both properties from that image instead of from the host. This is what makes the author workflow work on every Linux distribution, independent of the distribution's glibc and its packaged Rust toolchain, and on macOS, whose own platform cannot produce a Linux `.so` at all. The container build takes the invoking host's architecture, so the artifact matches the SLC built for that same architecture.

The `validate` subcommand performs ABI and dlopen-platform validation of a built `.so`. It checks the artifact against `EXA_UDF_ABI_VERSION` and `EXA_SDK_FINGERPRINT`, and against the SLC's glibc floor, builder rustc identity and library surface. That subcommand is specified separately in `tools/cargo-exaudf-validate` and runs on a Linux host only. `build` reports the same platform-fit findings as warnings so an author sees them at build time, and never as a build failure.

## Scenarios

<!-- DELTA:NEW -->
### Scenario: build --container produces an artifact the SLC accepts from any host

* *GIVEN* a UDF crate on a Linux host with `docker` or `podman` on `PATH`, whose glibc is newer than the SLC floor or whose `rustc --version` differs from the SLC's recorded builder rustc identity
* *WHEN* the author runs `cargo exasol-udf build --container`
* *THEN* the CLI MUST run the release build inside the builder image named by the committed builder record, so the artifact's glibc symbol versions and its baked rustc identity come from that image and not from the host, while its architecture comes from the invoking host and therefore matches the SLC built for that architecture
* *AND* it MUST write the artifact to a container-only target directory and print the path `target/slc/release/lib<crate>.so`, so a container build and a host build never overwrite each other's artifact
* *AND* it MUST mount the crate's Cargo workspace root and run as the invoking user, so a crate whose dependencies are path dependencies inside its own workspace builds unchanged and every file the build writes stays writable on the host
* *AND* the produced artifact MUST pass `cargo exasol-udf validate` on that same Linux host, because validate compares the artifact's SDK-version part against the CLI and its rustc-identity part against the committed builder record, and neither comparison reads the host's own rustc
<!-- /DELTA:NEW -->

### Scenario: build --container serves a host that cannot load the artifact it produces

* *GIVEN* a UDF crate on a macOS host with `docker` or `podman` on `PATH`, whose own platform cannot `dlopen` a Linux `.so`
* *WHEN* the author runs `cargo exasol-udf build --container`
* *THEN* the CLI MUST produce the artifact and print the path `target/slc/release/lib<crate>.so`, because the build runs inside the recorded builder image and no step of that path requires the host to be Linux
* *AND* it MUST NOT run, or require the author to run, `cargo exasol-udf validate` against that artifact on this host, because validation `dlopen`s the artifact and this host cannot
* *AND* it MUST state that the artifact satisfies the recorded glibc floor and the recorded builder rustc identity by construction on this path, so the author is not left expecting a local check that cannot run
<!-- /DELTA:NEW -->

<!-- DELTA:NEW -->
### Scenario: build --container reports a missing container engine

* *GIVEN* a host with neither `docker` nor `podman` on `PATH`
* *WHEN* the author runs `cargo exasol-udf build --container`
* *THEN* the CLI MUST exit non-zero and MUST name both engines as the requirement
* *AND* it MUST NOT fall back to a host build, because a silent fallback returns the artifact the flag exists to avoid
* *AND* when both engines are present the CLI MUST use `docker`, so the selection is deterministic rather than dependent on `PATH` order
<!-- /DELTA:NEW -->

<!-- DELTA:NEW -->
### Scenario: build warns when the host cannot produce an artifact the SLC accepts

* *GIVEN* a UDF crate on a host whose glibc is newer than the SLC floor, or whose `rustc --version` differs from the SLC's recorded builder rustc identity
* *WHEN* the author runs `cargo exasol-udf build` with no `--container` flag
* *THEN* the CLI MUST run the host build, then check the produced artifact through the same platform-fit check `validate` applies, so the two subcommands cannot disagree about one artifact
* *AND* it MUST print a warning naming each mismatching value, its recorded counterpart, and `--container` as the remedy
* *AND* it MUST exit zero, so an author who builds against a different SLC release is warned rather than blocked
* *AND* a host build whose artifact matches both recorded values MUST print no such warning
