## Premortem

Three failure stories, written before scoring.

1. **The database-host matrix never starts.** The `rhel` self-hosted runner runs RHEL 9. The leg downloads `it-runner`, which the `build` job linked against Ubuntu 24.04's glibc, and the loader refuses it with `GLIBC_2.38 not found` before an Exasol container exists. The leg that was added to prove a kernel claim fails on a symbol-version mismatch, which is the exact mechanism the plan's own Context is about. Routed to `[HIDDEN_DEPENDENCY]`.
2. **Every self-hosted leg fails on a missing file.** `it-runner` carries one `#[tokio::test]`, and task 6.5 hangs `distro_built_artifact_executes` off it. Only the `integration` job downloads the two distribution-built artifacts. Four `host-runtime` legs run the same binary and report `No such file or directory`, the failure shape `CLAUDE.md` already documents for the `test-udfs/*` allowlist. Routed to `[HIDDEN_DEPENDENCY]`.
3. **The author-host record cannot be written.** An implementer reads "one line per platform" and five families plus macOS, then reads "seven legs run in parallel" and a seven-image list holding two Ubuntu and two AlmaLinux references. The two statements cannot both hold, and the harness argument, the cache key and the drift test each assume the family is unique. Routed to `[REQUIREMENT_CONFLICT]`.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks 6.4 and 6.6; § Dependencies, the self-hosted runner entry
- Issue: `.github/workflows/ci.yml` compiles `it-runner` in the `build` job on `ubuntu-latest` and uploads it as the `it-test` artifact. Task 6.6 downloads that binary onto a self-hosted host of each family, and task 6.4's composite action runs it. `it-runner` is a glibc-dynamic binary, so it does not start on a host whose glibc is older than the one it was linked against. Decision [7] treats RHEL 8 and RHEL 9 as in scope through `almalinux:8` and `almalinux:9`, and its own research names RHEL 8, 9 and 10 on Exasol's list. A `rhel` runner of major 8 or 9 fails at the loader before any Exasol container starts, and an openSUSE Leap 15 runner fails the same way. § Dependencies states only the label triple, the host operating system and a container engine, and states no glibc or distribution version constraint. The plan's own Context makes this exact symbol-version mechanism central for the author artifact and never applies it to the harness that carries the new claim.
- Fix: Add a distribution version field to `dist/supported-database-hosts.txt` in plan.md task 4.1, naming the exact major version each family's claim covers, and state in plan.md § Dependencies that every `host-runtime` runner MUST provide a glibc at or above the glibc of the runner that builds `it-runner`. Add to task 6.4 a first step that compares the host glibc against that floor and fails with a message naming both versions, so a runner below the floor reports the cause instead of a raw loader error.
