# Plan Review Findings: add-cross-distro-compatibility (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 18 (Blockers: 5, Advisory: 13)
- Intent Fidelity blockers: 1

## Premortem

Three failure stories, written before scoring.

1. **The flag ships and the tool rejects its own output.** A Fedora author runs `cargo exasol-udf build --container`, gets an artifact, runs `cargo exasol-udf validate`, and reads `SDK fingerprint mismatch`. The CLI compares the artifact against its own baked fingerprint (`crates/cargo-exasol-udf/src/validate.rs:146`), which carries the author's rustc, not the container's. The feature's headline promise fails on the first host that needs it. Routed to `[REQUIREMENT_CONFLICT]`.
2. **The distribution matrix never goes green.** `dist/tests/distro_udf_build_test.sh` runs inside a distribution container, scaffolds a crate at a path that exists only in that container, and asks the host Docker daemon to bind-mount that path. The daemon mounts an empty directory. Every `--container` leg fails for a reason no one can reproduce locally, and the matrix is disabled. Routed to `[HIDDEN_DEPENDENCY]`.
3. **The published claim is wrong on the day it ships.** `docs/installation.md` states that openSUSE and AlmaLinux are supported by a plain `cargo exasol-udf build`. An author on openSUSE installs the distribution's own Rust package, builds, uploads, and gets `22002 VM crashed` from a fingerprint mismatch. The plan states this failure mode in its own Context and then publishes a claim that ignores it. Routed to `[COMPLETENESS_GAP]`.

## Intent Fidelity

#### [INTENT_DRIFT] BLOCKER
- Location: plan.md § Design/Context and § Implementation Tasks 1.8; decision-log.md § [7]
- Issue: the user asked that "the Rust SLC must be compatible with all Linux supported by Exasol". Exasol's published list names **database hosts**. The plan converts that into a claim about **author hosts**: the record is `dist/supported-author-hosts.txt`, and every verification leg builds a UDF on a distribution rather than running the SLC against an Exasol on that distribution. decision-log.md § [7] shows the planner saw the framing ("Exasol's system requirements page names ... as supported database hosts", "neither openSUSE nor Fedora appears on Exasol's database-host list") and then swapped the axis without recording the swap as a decision. The substitution may well be right, because the SLC carries its own root filesystem and the database-host distribution cannot reach inside it, but the plan never states that reasoning, so the whole shape of the work rests on an unrecorded reinterpretation of the request.
- Fix: Add a numbered decision to decision-log.md § Design Decisions, titled "The Exasol-supported Linux list constrains the author host, not the SLC runtime", stating the two readings of the request, the evidence that a database host's distribution cannot affect a staged-from-scratch SLC root, and the rejected alternative of adding a database-host distribution leg. Reference that decision from plan.md § Design/Context where the author-host framing is first used.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks 2.5, 2.10 and 4.1
- Issue: task 4.1 runs `dist/tests/distro_udf_build_test.sh` "inside each image with the repository and the Docker socket mounted at their own host paths". Task 2.10 has that script "scaffold a UDF crate against the in-tree SDK" and then run `build --container`. Task 2.5 has `build --container` "mount the crate's Cargo workspace root at its own absolute path" and "mount the cargo registry cache". A bind mount requested over a mounted Docker socket is resolved by the **host** daemon against the **host** filesystem, not against the calling container's filesystem. A crate scaffolded inside the distribution container, and a cargo registry cache inside it, do not exist on the host, so the sibling container starts with empty directories and the build fails or silently produces nothing. The plan states the socket mount and its security consequence in § Residual risk but never states this path-identity constraint, which decides whether the matrix can work at all. Two further gaps compound it: the plan never says where the `cargo-exasol-udf` binary under test comes from in each distribution container, and the § Verification checklist invokes `dist/tests/distro_udf_build_test.sh "$i"` from the host with an image reference, which reads as the script starting the container itself, while task 4.1 reads as CI starting the container around the script.
- Fix: In plan.md § Implementation Tasks, rewrite task 2.10 to state that the harness scaffolds the probe crate and places the cargo registry cache under the mounted repository path, so both paths are identical on the host and inside the container, and to state how `cargo-exasol-udf` is obtained in each image (build it from the mounted workspace with the distribution's toolchain). Rewrite task 4.1 and the § Verification checklist row "Distribution matrix" to use one invocation contract: state explicitly whether `dist/tests/distro_udf_build_test.sh <image-reference>` starts the distribution container itself or expects to be running inside it, and make both places agree.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 2.5 and 1.8; decision-log.md § [4]
- Issue: the SLC ships for x86_64 and aarch64 (`slim-image` scenario "SLC builds natively for the host architecture", and the CI `arm64` job). `build --container` runs the recorded builder image with no stated `--platform`, so the produced artifact takes the host's architecture. `dist/supported-author-hosts.txt` records one image reference per family with no architecture column, and `dist/tests/distro_udf_build_test.sh` runs on amd64 runners only. An Apple Silicon author following the `--container` instruction gets an aarch64 `.so`, which loads only against the aarch64 SLC. The plan never states that architecture is inherited from the host and never states which SLC an artifact then matches.
- Fix: Add one sentence to the `tools/cargo-exaudf` spec delta scenario "build --container produces an artifact the SLC accepts from any host" stating that the artifact takes the invoking host's architecture and matches the SLC built for that architecture, and add the same statement to task 2.9's documentation scope.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: plan.md § Implementation Tasks 4.1 and 4.4; § Verification checklist
- Issue: task 4.1 is one line that adds seven matrix legs, each of which installs a Rust toolchain, builds the workspace CLI, builds a scaffolded crate, and then starts a nested container build. Task 4.4 makes the `integration` job download artifacts produced by that job, which puts `distro-build` on the critical path before the three-version database matrix that today runs after `build-slc`. The plan states no runtime budget, no caching strategy, and no statement of whether `distro-build` runs on every push or on a schedule.
- Fix: Add a row to plan.md § Dependencies stating the expected wall-clock cost of the `distro-build` job and its effect on the `integration` job's critical path, and state in task 4.1 whether the job runs on every push or only on `main` and on a schedule.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: specs/_plans/add-cross-distro-compatibility/tools/cargo-exaudf/spec.md line 23; specs/tools/cargo-exaudf-validate/spec.md lines 21-26 (recorded, untouched by this plan); specs/_plans/add-cross-distro-compatibility/tools/cargo-exaudf-validate/spec.md line 22
- Issue: the new `build --container` scenario requires that "the produced artifact MUST pass `cargo exasol-udf validate` on that same host", under a GIVEN of a host "whose `rustc --version` differs from the SLC's recorded builder rustc identity". The recorded scenario "validate rejects an ABI or fingerprint mismatch" requires a non-zero exit whenever the artifact's `sdk_fingerprint` "differs from the current SDK", and the CHANGED scenario "validate accepts a compatible .so" still requires that "the `sdk_fingerprint` matches the current SDK". `crates/cargo-exasol-udf/src/validate.rs:146` implements exactly that comparison against `runtime_fingerprint()`, which is the CLI's own `EXA_SDK_FINGERPRINT` and therefore carries the rustc that compiled the CLI. On the very host the new scenario describes, the two requirements cannot both hold: a container-built artifact carries the builder's rustc, the CLI carries the author's, and validate exits non-zero. The validate delta's Background asserts the opposite, that comparing against the CLI fingerprint "passes on every host", which is true only when the artifact and the CLI were built by the same rustc. No task changes `validate.rs`'s fingerprint comparison, so the plan ships the contradiction.
- Fix: Add a `<!-- DELTA:CHANGED -->` block around the scenario "validate rejects an ABI or fingerprint mismatch" in the `tools/cargo-exaudf-validate` delta, restricting the comparison against the CLI's own `EXA_SDK_FINGERPRINT` to its SDK-version part and routing the rustc-identity part to the committed builder record. Change the same clause in the CHANGED scenario "validate accepts a compatible .so" so it names the SDK-version part, not the whole fingerprint. Add a task under plan.md § Implementation Tasks group 2 that splits `runtime_fingerprint()`'s comparison in `crates/cargo-exasol-udf/src/validate.rs` accordingly, and add a `validate` integration test row to § Verification that a container-built artifact validated by a CLI compiled by a different rustc exits zero.

#### [COMPLETENESS_GAP] BLOCKER
- Location: plan.md § Implementation Tasks 1.8; specs/_plans/add-cross-distro-compatibility/container/slc-platform-contract/spec.md lines 58-63
- Issue: three defects in one requirement. First, the spec says the list carries "its distribution family, its glibc version and the build path it uses", and task 1.8 records `<family> <image-reference> <build-path>`. The fields do not match, so no implementer can write the file or the checker from the plan. Second, the spec requires that "every listed platform whose glibc is at or below the recorded floor MUST be listed as supported by a plain `cargo exasol-udf build`", while plan.md § Design/Context states that "a distribution-packaged Rust toolchain never matches the fingerprint, whatever its version number". Both cannot be true: glibc alone does not decide the host build path, because the rustc identity decides it too. The published claim would therefore be wrong for any author who installs the distribution's own Rust package. Third, task 2.10 says the harness "installs the pinned toolchain for that distribution family", which reads either as a distribution package or as a rustup install of the pinned channel. The first makes every host leg fail by the plan's own reasoning, and the second is the only one that can pass, yet the plan never says which.
- Fix: In plan.md § Implementation Tasks 1.8, state the record's exact columns and make the `container/slc-platform-contract` delta scenario "Published platform support names one build path per author host" name the same columns. Add a fourth column or a stated rule for the toolchain source. Change the spec's second *AND* clause so the host build path requires both a glibc at or below the floor **and** a rustc whose identity equals the recorded builder identity, and change the third clause so the container-only path covers a platform that fails either condition. In task 2.10, replace "installs the pinned toolchain for that distribution family" with the exact install route, naming rustup and the exact toolchain version the builder record holds.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Implementation Tasks 1.9 and 1.10; specs/_plans/add-cross-distro-compatibility/container/slc-platform-contract/spec.md line 60
- Issue: task 1.9 requires the documentation to name `--container` "for every container-only platform and for macOS". Task 1.10 requires `dist/tests/supported_author_hosts_test.sh` to assert "the documentation names exactly the recorded platforms with the recorded build paths", and the spec requires that the statement "MUST name every platform the list names". Task 1.8 records "Ubuntu, RHEL, Debian, openSUSE and Fedora" only. macOS is therefore published as supported by a statement that a test asserts against a record that does not contain it. macOS also has no scenario, no task and no test anywhere in the plan, and `validate` cannot run on it at all, because the recorded scenario "validate accepts a compatible .so" requires the CLI to dlopen the Linux `.so` it checks. plan.md § Impact nevertheless states that "authors on macOS gain a supported build path".
- Fix: Decide one of two shapes and apply it throughout. Either add macOS to `dist/supported-author-hosts.txt` with the `container` build path, add a DELTA scenario to `tools/cargo-exaudf` covering `build --container` on a host whose CLI cannot dlopen the artifact, and state in `tools/cargo-exaudf-validate` that `validate` requires a Linux host. Or delete macOS from task 1.9, remove the macOS sentence from plan.md § Impact, and state in task 1.9 that the macOS note lives outside the record-checked support statement.

#### [COMPLETENESS_GAP] ADVISORY

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md § Implementation Tasks 1.1 and 1.3; specs/_plans/add-cross-distro-compatibility/container/slim-image/spec.md lines 58-61
- Issue: the record holds nested paths (`var/tmp`) beside top-level ones, and the spec requires that "a recorded path that already exists fails the build". Nothing states the creation order for a nested path whose parent is also recorded, so `var/tmp` created before `var` fails, and `var` created before `var/tmp` either needs `mkdir -p`, which defeats the collision rule, or needs a stated ordering. ## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Implementation Tasks 1.5, 1.6, 1.7 and 2.1; specs/_plans/add-cross-distro-compatibility/container/slc-platform-contract/spec.md line 52
- Issue: `crates/exasol-udf-sdk/build.rs` does not bake the raw `rustc --version` output. It maps every character that is not alphanumeric, `.` or `-` to `_`, takes the first 64 characters, and prefixes the SDK version. The spec requires that "the recorded identity MUST be the same string the SDK bakes into the fingerprint", while tasks 1.5 and 1.6 record and compare "the `rustc --version` identity". After this plan, the sanitize-and-truncate rule would have to be known by `crates/exasol-udf-sdk/build.rs`, by the Dockerfile builder stage (task 1.6), by the tarball test's shell comparison (task 1.7) and by `slc_surface.rs` (task 2.1), with nothing enforcing agreement. That is the same format decision reflected in four modules.
- Fix: Change plan.md task 1.5 so the builder record's identity line is derived from the compiled `exaudfclient`'s own baked fingerprint string rather than from `rustc --version`, leaving `crates/exasol-udf-sdk/build.rs` the single owner of the format. Restate tasks 1.6 and 1.7 as a string comparison against that derived value, and restate the spec clause to say the record holds the fingerprint's rustc part verbatim.

#### [SHALLOW_DESIGN] ADVISORY
- Location: plan.md § Implementation Tasks 1.6 and 4.3; specs/_plans/add-cross-distro-compatibility/container/slim-image/spec.md line 29
- Issue: task 1.6 adds `ARG BUILDER_IMAGE`, defaults it to the recorded reference, and then fails the build "when the argument differs from the recorded reference". Task 4.3 then passes `--build-arg BUILDER_IMAGE` read from that same record. The argument therefore has exactly one legal value, which the default already supplies, so the argument, the CI flag and the equality check together produce the behavior of a literal `FROM` plus one record check. A Dockerfile `ARG` before `FROM` also cannot take its default from a file, so the image reference stays duplicated between the Dockerfile literal and `slc-builder.txt`, which is the duplication the record exists to remove.
- Fix: Delete `ARG BUILDER_IMAGE` from plan.md task 1.6 and delete the `--build-arg BUILDER_IMAGE` clause from task 4.3, keeping the literal builder `FROM` plus the build-time check that the literal equals the record. Rewrite the `slim-image` delta scenario's GIVEN from "whose image reference is a build argument defaulting to the value the committed builder record names" to a statement that the builder `FROM` reference is verified against the committed builder record during the build.
