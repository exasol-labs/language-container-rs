# Plan Review Findings: fix-install-personal-local-db-port (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 8 (Blockers: 1, Advisory: 7)

## Premortem

Three failure stories, each routed into the taxonomy below.

1. **The fallback silently rots.** `resolves_local_defaults_when_db_port_absent` asserts `PORT` is `8563` after `reset_connection_globals` already set `PORT=8563`, so it passes whether or not `resolve_local_connection` touched `PORT`. A later refactor drops the `deployment_field` default argument or reorders the `CLI_PORT` precedence; descriptors written by an older launcher (no `connection.dbPort`) resolve `PORT=""`, the DSN becomes `127.0.0.1:`, and the suite stays green. → BLOCKER, Task Breakdown.
2. **The false premise outlives the fix.** A maintainer adding a local-only setting reads `scripts/install.sh:396` — "Personal-local always talks to the VM's local SQL port" — believes the SQL endpoint is VM-fixed, and hardcodes a port in the new path. Issue #83 returns in a different function. → Advisory A1.
3. **`--help` dies mid-plan.** Task 2 renames `PERSONAL_DB_PORT`; task 3 fixes the only other reference, in `usage()`. A commit that lands task 2 alone makes `scripts/install.sh --help` abort under `set -u` with `PERSONAL_DB_PORT: unbound variable`. → Advisory A2.

## Intent Fidelity

No objection — axis checked against issue #83's body (fetched via `gh issue view 83`) and the four interview answers. Every scoped item is present and no scoped item is dropped: `.connection.dbPort` read for local (task 2), `--port` honored for local via the existing `CLI_PORT` sentinel (task 2 + decision [3]), minimal extraction reusing `deployment_field` and drivable from the sourced harness (task 1/2 + decision [1]), spec background corrected plus a local scenario mirroring the cloud one (delta lines 10 and 67-76). The banner print, the `deployment_ssh_port` dedup, and password/scope ownership stay out (decision [2], [8]).

The three reported scope additions are warranted, not creep:
- `PERSONAL_DB_PORT` → `PERSONAL_DB_PORT_DEFAULT`: three sites in one file (verified: `scripts/install.sh:41`, `:91`, `:401` are the only occurrences), and the constant's meaning genuinely changes from fact to fallback.
- `docs/installation.md` (lines 57, 81, 118, 120 verified verbatim): the user-facing doc asserts "fixes the SQL host/port at `127.0.0.1:8563`" and "`ALTER SYSTEM SET SCRIPT_LANGUAGES` over `8563`". Shipping the fix without these leaves the docs describing the removed behavior — completion, not gold-plating.
- The two extra scenario amendments follow necessarily. "Connection details are read fresh on every run" previously covered the SSH port only; the delta attributes each port's churn to its own cause (`exasol stop`/`start` for SSH, `exasol config set --ports db:<port>` for SQL) rather than over-claiming. "A registered Rust UDF executes on Personal" said "invoked over `8563`", which is the exact assertion the plan disproves.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: `container/personal-install/spec.md` § Scenario: Local connection details resolve from the deployment directory (delta line 73)
- Issue: the clause reads "the DB port MUST come from `connection.dbPort`, defaulting to `8563` **only** when the field is absent". `deployment_field` substitutes the default when the value is absent **or empty** (`scripts/install.sh:202-204`: `if [[ -z "$value" ]]; then value="$default"; fi`), so a descriptor carrying `"dbPort": ""` also resolves `8563`. The word "only" turns a description into an exclusivity claim the implementation contradicts, and a test author could legitimately write an empty-value fixture asserting failure. The existing cloud scenario (recorded spec line 92) says "defaulting to `8563` when the field is absent" without "only" — two wordings for one field.
- Fix: In `container/personal-install/spec.md`, change the delta clause to "*AND* the DB port MUST come from `connection.dbPort`, defaulting to `8563` when the field is absent or empty, so on a host running several local deployments the install targets the database named by `--deployment` rather than whichever database answers `8563`".

## Design Depth

No objection — axis checked per `/speq:design-philosophy`'s Quick Diagnostic. `resolve_local_connection` is shallow by volume, and the plan says so rather than overselling it; the extraction was mandated by the interview, so its existence is settled and only its execution is in scope. One sentence covers its responsibility, and after the change exactly one module owns "where a local deployment's SQL endpoint is" — today that decision is split between a file-level constant and two lines of `main`. Assigning the globals `HOST`/`PORT` instead of printing a value is coupling, but it is the codebase's established seam (`resolve_cloud_connection`, `scripts/install.sh:232-265`) and printing could not carry two values; inventing a second convention here would leak the decision across two shapes. Routing `.connection.dbPort` through `deployment_field` removes a genuine back-door leakage: the same descriptor field currently has one parser for cloud and a hardcoded constant for local. Decision [4] correctly refuses to give one field two validation behaviors.
