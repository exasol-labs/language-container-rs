### scripts/tests/install-personal-test.sh

#### [MISSING_BOUNDARY_TEST] `require_cloud_bfs_password`'s success path lost its only assertion in the extraction
- Location: line 347 (`cloud_requires_operator_bfs_password`), lines 356 and 358
- Issue: The test asserts only that an empty `BFS_PASSWORD` fails. Nothing asserts that a supplied one returns `0`, so the spec clause "*AND* when `--bfs-password` is supplied, the cloud install MUST proceed" (`container/personal-install/spec.md:134`) is unasserted. Confirmed by mutation: replacing `if [[ -z "$BFS_PASSWORD" ]]; then` with `if true; then` in `require_cloud_bfs_password` — making every cloud install fail even with a correct password — leaves the whole suite green (exit 0, zero FAILs). This is a coverage regression introduced by moving the check out of the resolver: the same mutation applied to the committed pre-refactor `resolve_cloud_connection` fails three tests (`resolve_cloud_connection succeeds given a complete cloud descriptor`, `… with CLI overrides`, `… with dbPort/username absent`), because those tests set `BFS_PASSWORD="bfspw"` and asserted `rc` was `0`. Decision [12] extracted the function specifically to keep the check assertable, and then the positive half of the assertion went missing. Separately, both existing check texts say "cloud resolution", but the function under test performs no resolution at all — it reads only `BFS_PASSWORD`.
- Fix: In scripts/tests/install-personal-test.sh, function `cloud_requires_operator_bfs_password`, append after the line-358 `check`: a blank line, then `BFS_PASSWORD="bfspw"`, then `require_cloud_bfs_password >/dev/null 2>&1`, then `check "a supplied --bfs-password lets the cloud install proceed" "0" "$?"`. In the same function change the line-356 check text from `"an empty --bfs-password fails cloud resolution"` to `"an empty --bfs-password fails the cloud BucketFS-password requirement"`, and the line-358 check text from `"the error names --bfs-password as the missing Personal requirement"` to `"the error names --bfs-password as the missing BucketFS credential"`.

#### [DUPLICATE_TEST] The second `HOST resolves from connection.host` assertion is tautological
- Location: line 128 (second occurrence within `resolves_local_connection_from_descriptor`)
- Issue: The assertion re-reads the value the *first* resolve produced and can never independently fail. `resolve_deployment_connection` assigns `HOST` only under the guard `[[ -z "$HOST" ]]` (`scripts/install.sh:259`), and `HOST` is already `descriptor.example` when the second resolve is entered, so the second resolve provably cannot touch `HOST`. Keep the line-119 `HOST` assertion, the line-127 `dbPort`-freshness assertion, and the `HOST=""` line at 133 with its comment unchanged.

## Expert fixes

### scripts/tests/install-personal-test.sh

#### [MISSING_BOUNDARY_TEST] The cloud call site's empty `default_host` is unasserted across the whole suite
- Location: lines 305, 335, 372, 392, 412 (every `resolve_deployment_connection "$dir" ''` call site)
- Issue: `default_host` is the entire reason the unified function takes a second argument, and the spec makes it a MUST: "Cloud has no host default: `deployment.json` MUST carry `connection.host` or the operator MUST pass `--host`" (`container/personal-install/spec.md:18`). No test exercises it. All five cloud tests supply `connection.host` in their fixture, so the descriptor value wins and the default is never consulted. Confirmed by mutation: replacing the resolver's `deployment_field "$dir" '.connection.host' "$default_host"` with `deployment_field "$dir" '.connection.host' '127.0.0.1'` — giving cloud a silent localhost host default and discarding the argument entirely — leaves the whole suite green (exit 0, zero FAILs). `resolves_local_host_default_when_absent` does not catch it because it expects `127.0.0.1` too. The real-world consequence of that regression is a cloud Personal install registering `SCRIPT_LANGUAGES` against the operator's own machine, which is #83's failure mode on the other backend. plan.md task 5 asserts the `''` argument "is what keeps cloud's 'no host default' rule asserted"; nothing asserts it.
- Fix: In scripts/tests/install-personal-test.sh, add a function `cloud_requires_host_when_descriptor_omits_it` immediately above `cloud_requires_db_password`, and register it in the `run` list on the line directly above `run cloud_requires_db_password`. Body: declare `local dir rc`; `dir="$(mktemp -d)"`; write `{"backend":"aws","connection":{"dbPort":8563,"username":"sys"}}` (no `host` key) to `"$dir/deployment.json"` and `{"dbPassword":"secret"}` to `"$dir/secrets.json"`; call `reset_connection_globals`; call `resolve_deployment_connection "$dir" '' >/dev/null 2>&1`; capture `rc=$?`; then `check "cloud resolution fails when connection.host is absent and no --host is given" "1" "$rc"` and `check "HOST stays empty because the cloud call site passes no host default" "" "$HOST"`; end with `rm -rf "$dir"`. Do not set `BFS_PASSWORD` in this test — the resolver does not read it.

#### [ASSERTION_FREE_TEST] `resolves_cloud_connection_from_descriptor`'s PORT and USER assertions cannot fail
- Location: lines 310 and 311, guarded by `reset_connection_globals` at line 303
- Issue: `reset_connection_globals` writes `PORT=8563` and `USER=sys` (lines 260-261), and the fixture descriptor carries exactly `"dbPort":8563` and `"username":"sys"` (line 299). Both assertions therefore pass whether or not the resolver ever assigns either global. Confirmed by mutation: dropping the `else PORT="$descriptor_port"` and `else USER="$descriptor_user"` branches from the resolver — so the descriptor is never read for either field — leaves all five assertions in this test reporting `ok`. This is the exact vacuity pattern the decision log records twice (`[plan-review]` round-1 BLOCKER and decision [15]); decision [15] applied the sentinel to `resolves_cloud_defaults_when_connection_fields_absent` but left this test, whose fixture values happen to equal the reset values, unguarded. It is the test the plan's § Scenario Coverage maps to "Cloud connection details resolve from the deployment directory", whose two THEN clauses ("the DB port MUST come from `connection.dbPort`", "the DB user MUST come from `connection.username`", spec lines 118-119) are asserted only here.
- Fix: In scripts/tests/install-personal-test.sh, function `resolves_cloud_connection_from_descriptor`, insert `  PORT="unresolved"` and `  USER="unresolved"` on the two lines immediately after `reset_connection_globals` (line 303), matching the sentinel pattern already used by `resolves_cloud_defaults_when_connection_fields_absent` (lines 389-390). Leave the fixture descriptor, the expected values `8563`/`sys`, and every check text unchanged.

### scripts/install.sh

#### [SWALLOWED_ERROR] A failed descriptor read is discarded, so resolution can succeed with an empty PORT and USER
- Location: lines 255-257 (the three `|| true` accessor captures), against the presence checks at 267-274
- Issue: `deployment_field` returns 1 and prints nothing when the descriptor is unreadable — it fails *before* substituting the caller's default (`scripts/install.sh:200-203`). The three `|| true` captures discard that status, so `descriptor_port` and `descriptor_user` land empty and the documented defaults (`PERSONAL_DB_PORT_DEFAULT`, `sys`) silently do not apply. Only `HOST` and `PASSWORD` have presence checks, so whenever both are supplied on the command line the function returns `0` with empty `PORT` and `USER`. Probe-confirmed against the working tree: `HOST="cloud.example" PASSWORD="pw"` plus an empty directory yields `rc=0  HOST=[cloud.example]  PORT=[]  USER=[]`, which `main` would interpolate into the malformed DSN `exasol://:pw@cloud.example:?validateservercertificate=0`. plan.md § Decision claims "An unreadable `deployment.json` still fails … so `HOST` stays empty and the host check fires" — true only when no `--host` is passed. Today the malformed DSN is unreachable from `main` solely because `deployment_backend` runs first and dies (line 424), i.e. the resolver's safety rests on an undocumented ordering contract that nothing enforces — the guardrail "if a second call requires a first, make it unreachable without it". The resolver's own doc comment (lines 243-247) advertises the defaults as part of its contract, so the next call site inherits the hole.
- Fix: In scripts/install.sh, function `resolve_deployment_connection`, add a guard clause as the first statement after the `local` declarations (after line 251, before the accessor comment): `if [[ ! -r "$dir/$DEPLOYMENT_DESCRIPTOR" ]]; then`, `echo "error: no readable deployment descriptor at $dir/$DEPLOYMENT_DESCRIPTOR" >&2`, `return 1`, `fi`. Then update the function's doc comment: change "Returns 1 (never exits) on a missing host or password" (line 243) to state that it returns 1 (never exits) on an unreadable `deployment.json` or a missing host or password, and that the guard clause is what makes the three documented descriptor defaults meaningful — a failed `deployment_field` read yields no default, so the read must fail the function rather than fall through. Keep the three `|| true` captures, their comment, the precedence assignments, and both existing presence checks exactly as they are. Also add a test to scripts/tests/install-personal-test.sh: a function `unreadable_descriptor_fails_even_with_cli_overrides`, registered in the `run` list directly below `run resolves_local_connection_from_descriptor`, which creates an empty `mktemp -d` directory (no `deployment.json`, no `secrets.json`), calls `reset_connection_globals`, sets `HOST="cloud.example"` and `PASSWORD="pw"`, calls `resolve_deployment_connection "$dir" '' >/dev/null 2>&1`, captures `rc=$?`, and asserts `check "an unreadable descriptor fails even when --host and --password are supplied" "1" "$rc"` plus `check "PORT is not left empty by a failed descriptor read" "8563" "$PORT"`; end with `rm -rf "$dir"`. Write that test first and confirm it fails against the current code before adding the guard clause.
