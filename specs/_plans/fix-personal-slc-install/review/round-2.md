## Premortem

Two failure stories drove the fresh pass.

1. A developer rebuilds the SLC, re-runs `scripts/install.sh --deployment default`, and answers `n` to the launcher's replacement prompt by reflex. The launcher exits `0` and changes nothing. The install script asks the launcher what is recorded, finds the alias `RUST` and the source `…/target/slc/lc-rs.tar.gz`, which is the exact path it just passed, and reports success. Every later UDF runs against the previous container. Routed to Feasibility, `[UNSTATED_ASSUMPTION]`.
2. The merged spec library tells a future implementer that the launcher's install "does nothing when the source path, the language and the activation are all unchanged". A test written from that sentence asserts that a second run with a rebuilt tarball is a no-op. The launcher replaces the container instead, because it compares the container, not the path. The test is deleted as flaky, and the real contract is lost. Routed to Requirement Quality, `[REQUIREMENT_CONFLICT]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: decision-log.md § Design Decision 10 (Rationale) and § Design Decision 4; plan.md § Implementation Tasks 3.1 and 3.4; `container/personal-install-local` spec delta § "The delegated local install verifies what the launcher recorded"
- Issue: the stable tarball path removes the only difference the post-install verification measures, so the check the plan relies on can no longer fail. Decision 4 states "Verifying the recorded source turns both the declined replacement and any silent no-op into a clear failure". The spec scenario states "it MUST fail when that entry is absent or records a different source, because the launcher reports a replacement the operator declined as a run that exited zero and changed nothing". Both hold only while consecutive runs pass different source strings. Under Decision 10 every run passes `$REPO_ROOT/target/slc/lc-rs.tar.gz`. A declined replacement leaves the entry the previous run recorded, whose source is that same string, so the comparison succeeds and the install reports success over an unchanged deployment. Decision 10's rationale asserts the opposite: "A stable path also restores the launcher's unchanged-source no-op, which the verification step in Decision 4 relies on to tell a real install from a declined replacement". A real install, a no-op and a declined replacement now all present the same recorded source. Checked against the launcher installed on this workstation: `exasol slc list -d default --json` returns `type`, `language`, `alias`, `source`, `installed` and `available` for a custom entry and no container digest, so the listing carries no other field that separates the three outcomes. The launcher's install command does separate them. It offers `-j`, its result object carries `alreadyInstalled`, `replaced` and `changed`, and a declined prompt aborts with "Aborted; no changes were made." and exit `0`. Its prompt goes to stderr, so capturing stdout keeps the prompt visible and answerable.
- Fix: In plan.md § Implementation Tasks 3.3, require `launcher_install_command` to pass the launcher's JSON output flag. In task 3.4, rename the verification to read the launcher's install result: fail unless stdout carries a result object whose `changed` or `alreadyInstalled` is true, and treat empty stdout as the declined replacement. Keep the `slc list` alias and source assertion as a second check. In `container/personal-install-local` § "The delegated local install verifies what the launcher recorded", replace the source-comparison THEN and its AND with a requirement that the install read the launcher's own reported outcome and fail unless that outcome reports the container as recorded or already installed. In decision-log.md Design Decision 4, replace "Verifying the recorded source" with the outcome check, and delete the sentence in Design Decision 10 claiming the stable path restores what the verification relies on.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: decision-log.md § Design Decision 10; plan.md § Impact
- Issue: `target/` is the cargo build tree, and `cargo clean` deletes it. The project's own command list in `CLAUDE.md` and `specs/mission.md` makes `cargo` the routine tool in this repository. After any `cargo clean`, every recorded source points at a deleted file again, which is the defect round 1 raised. Decision 10 weighs `dist/` and a per-deployment location but never weighs the deletion risk of the location it picks, and no line tells the operator that a clean invalidates the record.
- Fix: Add the consequence to decision-log.md Design Decision 10 Rationale in one sentence: `cargo clean` removes the staged tarball, so the recorded source stops resolving until the next install. Add the same sentence to plan.md § Impact, and require task 4.1 to state it in the `docs/installation.md` Personal section.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `specs/_plans/fix-personal-slc-install/container/personal-install-local/spec.md` line 94, § "Re-running the delegated local install replaces the container"; decision-log.md § Design Decision 10 Alternatives
- Issue: the narrowed no-op clause states a rule the launcher does not apply, and it contradicts the next line of its own scenario. Line 94 reads "does nothing when the source path, the language and the activation are all unchanged". Line 95 then requires the deployment to end "recorded against the rebuilt tarball", and plan.md § Manual Testing expects the second run to prompt for a replacement and record the rebuilt tarball. A rebuilt tarball keeps the same source path under Decision 10, so the two lines demand opposite outcomes from one run. The launcher decides from the container, not the path: on a repeat install of the same container it reports "<alias> is already installed with this container. Nothing to do.", and its `--source` accepts a local path or an HTTPS URL that it records verbatim. The term "the activation" also appears nowhere else in the plan or the spec library, so the clause is not testable as written. Decision 10 Alternatives repeats the same wrong rule: "a freshly named directory on every run would make the launcher's no-op case unreachable". The dangling-record reason in that same sentence stands on its own and is the reason to keep.
- Fix: In `container/personal-install-local` § "Re-running the delegated local install replaces the container", replace "does nothing when the source path, the language and the activation are all unchanged" with "does nothing when the deployment already holds that same container under that alias and language". In decision-log.md Design Decision 10 Alternatives, delete the clause "and a freshly named directory on every run would make the launcher's no-op case unreachable", keeping the recorded-deleted-path reason.

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md § Implementation Tasks 3.1 and 3.3; `container/personal-install-local` spec delta § "The delegated local install hands the tarball to the launcher" and § "Re-running the delegated local install replaces the container"
- Issue: the `--skip-build` path can hand the launcher a relative path, and nothing in the plan prevents it. `scripts/install.sh` line 481 sets `SKIP_BUILD=1` for any `SLC_TARBALL`, and line 503 sets `TMP_TAR="$SLC_TARBALL"` unchanged, which task 3.1 states it leaves alone. The spec requires "the tarball's absolute local path as the source" and a recorded source that "MUST name a path that still exists after the install script exits". The launcher records the `--source` string as given, so `SLC_TARBALL=./lc-rs.tar.gz` produces a record that resolves only from the directory the run started in. `docs/installation.md` documents `SLC_TARBALL` for exactly this path.
- Fix: In plan.md § Implementation Tasks 3.1, require the script to resolve `TMP_TAR` to an absolute path in both branches before step 2, and to fail with a clear error when `SLC_TARBALL` names no readable file. Add a failing test `delegated_install_absolutizes_a_relative_tarball` to plan.md § Implementation Tasks 3.2 and to § Verification, Scenario Coverage under "The delegated local install hands the tarball to the launcher".
