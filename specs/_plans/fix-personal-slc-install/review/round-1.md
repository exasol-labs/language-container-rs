# Plan Review Findings: fix-personal-slc-install (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 13 (Blockers: 4, Advisory: 9)
- Intent Fidelity blockers: 0

## Premortem

Four failure stories drove the axis pass below.

1. Every Personal deployment records a custom SLC whose `source` names a `/tmp/slc-XXXXXX/lc-rs.tar.gz` that no longer exists, because `scripts/install.sh` deletes its build directory on exit. Nobody can tell which tarball is installed, and any launcher action that re-reads the source fails. Routed to Feasibility, `[HIDDEN_DEPENDENCY]`.
2. Issue #110 stays open. The container fix ships and the SLC installs, but the reporter still cannot run a UDF, because `docs/installation.md` lost its only working instruction for copying a UDF `.so` into a local deployment and nothing concrete replaced it. Routed to Requirement Quality, `[AMBIGUOUS_REQUIREMENT]`.
3. The recorded spec library states two opposite mechanism-selection rules for `container/personal-install-local`. A later change follows the Background text, a later test follows the scenario text, and the two diverge. Routed to Requirement Quality, `[REQUIREMENT_CONFLICT]`.
4. The skeleton fix was verified on macOS arm64 only. The reporter's Linux/Podman x86_64 deployment still crashes, and the issue was closed on evidence from a different platform. Routed to Feasibility, `[UNSTATED_ASSUMPTION]`.

## Intent Fidelity

No objection — axis checked. The three interview answers are honored. One plan covers both defects. No task, spec delta or decision reads or compares a Personal version string, matching "We shouldn't compare versions though". Both mechanisms stay reachable, matching "Support both old and new". The delegated design matches "We could delegate to `exasol slc custom install`". The deviation from the user's suggested directory heuristic is recorded as Design Decision 1 with evidence, and the brief authorizes judging it on merits; findings on it appear under Feasibility. No gold-plating: the `0.28.1` bump follows the project's own version rule, and `verify_launcher_recorded_slc` is justified by the declined-replacement case in Decision 4.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks 3.2 and 3.3; `container/personal-install-local` spec delta § "Re-running the delegated local install replaces the container" and § "The delegated local install verifies what the launcher recorded"
- Issue: the source path the delegated mechanism hands the launcher is deleted before the run ends, and the plan never models that. `scripts/install.sh` lines 489-496 build into `TMP_DIR=$(mktemp -d /tmp/slc-XXXXXX)` under `trap 'rm -rf "$TMP_DIR"' EXIT`, and set `TMP_TAR="$TMP_DIR/lc-rs.tar.gz"`. The launcher persists that string verbatim: `exasol slc list -d default --json` on this workstation returns `"source": "https://github.com/exasol-labs/language-container-rs/releases/download/v0.28.0/lc-rust-0.28.0-aarch64.tar.gz"` for the installed custom entry. Three consequences follow, none of them stated. First, every delegated install leaves a persistent record pointing at a deleted path. Second, the temp directory is freshly named on every run, so the spec clause "does nothing when the container is unchanged" is unreachable: the source never matches the previous run, and every re-run is a prompted replacement. Third, task 3.3's comparison of the recorded source against "the tarball just passed" only ever compares a string that cannot recur, so it detects a declined replacement but certifies a record that is already dangling.
- Fix: In plan.md § Implementation Tasks, add a task before 3.2 that stages the built tarball at a stable path outside the `EXIT`-trapped temp directory (for example `dist/lc-rs.tar.gz` in the repository, or a documented per-deployment location) and makes `launcher_install_command` pass that path, so the recorded source survives the run. State the chosen path and why in a new Design Decision in decision-log.md, listing "pass the temp-directory path" as the rejected alternative with the `mktemp`/`trap` evidence above. In the `container/personal-install-local` spec delta § "Re-running the delegated local install replaces the container", delete the clause "and does nothing when the container is unchanged" or rewrite it to hold only when the source path is unchanged. Add an `AND` to that scenario requiring the source the launcher records to name a path that still exists after the install script exits.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: decision-log.md § Design Decision 1; plan.md § Design, Architecture
- Issue: Decision 1 rejects the directory-first rule on the strength of one mixed case, "a deployment directory created by an older Personal release keeps `.connection.sshPort` and `local/node_access.pem` until the next start rewrites them, so a directory-first rule takes the SSH path on a machine where the supported path exists". That argument assumes the current launcher's custom-SLC install succeeds against such a directory. `notes/planning.md` § Not checked states the opposite: "Whether a deployment directory from an older release survives a start under a current launcher" was not verified. If it does not, the plan's rule selects a mechanism that fails on exactly the case the rule exists to serve, with no fallback, because the spec requires the delegated mechanism "whatever the deployment directory holds".
- Fix: Add the assumption to decision-log.md Design Decision 1 under a new `Assumptions:` field, worded as "the launcher's custom-SLC install command succeeds against a deployment directory created by an older release", and name it as unverified. Add a row to plan.md § Manual Testing that runs `scripts/install.sh --deployment <name>` against a deployment directory carrying `.connection.sshPort` and `local/node_access.pem` under a launcher that offers the custom-SLC command, with the expected output "the delegated install completes and the launcher records the tarball".

#### [NFR_IGNORED] ADVISORY
- Location: plan.md § Impact
- Issue: no migration path is modeled for an operator who already installed over the SSH mechanism and now switches to the delegated one. plan.md claims "the container moves out of BucketFS into the launcher's own store, where `exasol slc list` and `exasol slc remove` reach it". Nothing in the plan removes the old copy: the SSH mechanism extracted the tarball into `/var/lib/exa/bucketfs/<service>/<bucket>/<slc-name>/` on the VM, and the delegated path issues no SSH and no SQL, so the old tree and the old `RUST=` entry it registered stay behind. Whether the launcher's own `SCRIPT_LANGUAGES` write replaces or collides with a pre-existing `RUST=` entry written by `script_languages_with_rust_entry` is untested and unstated.
- Fix: In plan.md § Impact, replace "the container moves out of BucketFS into the launcher's own store" with a statement that the delegated install adds a launcher-owned container and leaves the previous BucketFS copy in place. Add a row to plan.md § Manual Testing that runs the delegated install on a deployment previously installed over the SSH mechanism, with the expected output "exactly one `RUST=` entry in `SCRIPT_LANGUAGES`, naming the launcher-owned location". State in § Impact what the operator must do to remove the orphaned BucketFS copy.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Impact; decision-log.md § Design Decision 4
- Issue: the delegated install restarts the operator's database, and the plan records that only in one Impact sentence. `exasol slc custom install --help` on this workstation offers `--no-restart  Record the custom SLC without restarting; it activates on the next start`, which Decision 4 never weighs among its alternatives. No spec scenario records the restart, so the permanent spec library will not carry a behavior that drops every open session on a machine the operator may be using. Decision 4 also states "The launcher approves its own prompts when the run has no terminal, so a scripted run still completes". The launcher's own help qualifies that: `--auto-approve  Approve confirmation prompts, which a run with no terminal also does automatically except for local runtime host preparation`. A terminal-free run against a local deployment that needs host preparation is therefore not covered by the claim.
- Fix: Add `--no-restart` to decision-log.md Design Decision 4 § Alternatives with the reason it was not taken. Add an `AND` to the `container/personal-install-local` spec delta § "The delegated local install hands the tarball to the launcher" recording whether the delegated install restarts the deployment. In plan.md § Impact, qualify the auto-approval sentence with the local-runtime-host-preparation exception quoted above.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `specs/_plans/fix-personal-slc-install/container/personal-install-local/spec.md` lines 4 and 10, against lines 16 and 62
- Issue: the feature states two opposite mechanism-selection rules. Line 4 (DELTA:CHANGED feature summary) says the install works "by reading what the deployment directory offers and then either reconciling BucketFS over SSH into the VM filesystem or handing the container to the Personal launcher's own custom-SLC command". Line 10 (DELTA:CHANGED Background) says "The local install therefore has two mechanisms, and the deployment directory decides which one applies." Line 16 of the same Background says "The launcher's own capability chooses between the two on every run", and line 62 of the new scenario requires "it MUST choose the delegated mechanism whenever the launcher offers its custom-SLC install command, whatever the deployment directory holds". A reader cannot derive one rule from this feature, and both wordings will be merged into the permanent library.
- Fix: In the `container/personal-install-local` spec delta, rewrite line 4 to read that the install chooses its mechanism from the launcher's own capability, then either reconciles BucketFS over SSH or hands the container to the launcher's custom-SLC command. Replace line 10's clause "and the deployment directory decides which one applies" with "and the launcher's own capability decides which one applies". Leave lines 16 and 62 unchanged.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `specs/_plans/fix-personal-slc-install/container/personal-install/spec.md` line 28, § "Connection details are read fresh on every run"
- Issue: the GIVEN states a false causal rule. It reads "a Personal deployment whose `deployment.json` carries `connection.sshPort` and `connection.dbPort`, and a key at `local/node_access.pem`, which selects the SSH mechanism". Under Design Decision 1 those inputs do not select the SSH mechanism. The `container/personal-install-local` delta requires the delegated mechanism "whenever the launcher offers its custom-SLC install command, whatever the deployment directory holds", so a deployment with both SSH inputs still takes the delegated path on a current launcher. The mapped test `reads_ssh_port_from_deployment_json` exercises the accessors only, so nothing catches the contradiction.
- Fix: In the `container/personal-install/spec.md` delta § "Connection details are read fresh on every run", replace the trailing clause ", which selects the SSH mechanism" with ", on a launcher that offers no custom-SLC install command, so the SSH mechanism is selected".

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: plan.md § Implementation Tasks 4.1; plan.md § Design, Non-Goals; plan.md § Manual Testing
- Issue: task 4.1 is not executable as written, and the gap it leaves breaks the plan's own end-to-end verification. It instructs "Replace the `sshPort` and `node_access.pem` snippet for copying a UDF `.so` with guidance that applies to a deployment without SSH inputs", and names no mechanism. `docs/installation.md` lines 118-136 currently hold the only documented way to get a UDF `.so` onto a local deployment, and it is the SSH snippet the task deletes. § Non-Goals forbids the obvious replacement: "Adopt the launcher's current key or shared directory to rebuild a file transfer of our own." Without a stated replacement, plan.md § Manual Testing's row "Create the scalar UDF from `docs/writing-a-udf.md`, then `SELECT health_check()`", which is the only end-to-end check of defect A, cannot be run on a current local deployment. The mechanism exists and is checkable: on this workstation `~/.exasol/personal/deployments/default/local/runtime/vm-shared/exa/bucketfs/bfsdefault/default/udf` is a host directory, and the deployment's `bucketfs.conf` maps `/exa/bucketfs/bfsdefault/default` to `/buckets/bfsdefault/default`, so a plain host-side `cp` lands the `.so` at `/buckets/bfsdefault/default/udf/`.
- Fix: In plan.md § Implementation Tasks 4.1, name the replacement explicitly: copy the `.so` into `~/.exasol/personal/deployments/<name>/local/runtime/vm-shared/exa/bucketfs/<service>/<bucket>/udf/` with `cp`, which the deployment's `bucketfs.conf` maps to `/buckets/<service>/<bucket>/udf/`, and keep the existing SSH snippet for a deployment that still publishes SSH inputs. In plan.md § Design, Non-Goals, scope the existing bullet to the install script by rewriting it as "Rebuild a file transfer of our own inside `scripts/install.sh` from the launcher's current key or shared directory", so the documentation guidance is not excluded by it.

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md § Dependencies against § Implementation Tasks 2.4 and the `container/personal-install-local` spec delta § "The launcher's capability selects the local install mechanism"

That section promises "The delegated install path requires the `exasol` launcher on `PATH` with an `slc custom install` subcommand. The install script detects its absence and reports it." An operator with no `exasol` on `PATH` at all is told to upgrade a launcher they do not have.
- Fix: In plan.md § Implementation Tasks 2.3, require `launcher_offers_custom_slc` to distinguish "no `exasol` on `PATH`" from "`exasol` present without the subcommand". ## Task Breakdown

#### [TRACEABILITY_GAP] ADVISORY
- Location: plan.md § Implementation Tasks 3.6 and 3.7
- Issue: three edits the change requires have no task. First, `scripts/install.sh` lines 5-26 carry a header comment block that describes the `--deployment` local path as SSH-only ("`\"local\"`: Personal publishes only the SQL port from its VM ... so the tarball travels over SSH"). Task 3.7 covers `usage()` and the `--deployment` help only, so the header will contradict the code. Both call sites read its answer and nothing else", but task 3.6 does not say the answer is computed once. Two calls run the launcher help probe twice and can disagree within one run.
- Fix: Extend plan.md § Implementation Tasks 3.7 to also rewrite the `scripts/install.sh` header comment block at lines 5-26 so it describes both local mechanisms. Extend task 3.6 to state that `personal_local_mechanism` runs once, that its answer is stored in a variable both the selection block and the transport block read, and that the delegated path requires `exasol` rather than `exapump`.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Implementation Tasks 2.3 and 3.2
- Issue: the launcher's `--source` option name is a single decision reflected in two planned functions with nothing enforcing agreement. Task 2.3 requires `launcher_offers_custom_slc` to return success "only when its stdout names that command's `--source` option", and task 3.2 requires `launcher_install_command` to assemble a command passing the tarball. This is the back-door leakage Design Decision 6 explicitly avoids for the skeleton list, where "two modules would independently assume the same list, with nothing enforcing agreement". If the launcher renames the option, the probe reports the command as absent and the run silently falls back to the SSH mechanism or fails on a prerequisite, rather than surfacing the real cause.
- Fix: In plan.md § Implementation Tasks 2.3, require a single shell constant holding the launcher's source option name, declared beside the other Personal-transport constants in `scripts/install.sh`, and require both `launcher_offers_custom_slc` and `launcher_install_command` to read it. Name the constant in the § Patterns table row "Probe the usage line, not the exit status".
