## Round-3 Blocker Recheck

- **Resolved: [NFR_IGNORED] The removal target's own name component was never validated.**
  Two independent guards now stand before the `rm -rf`, and both are reachable on every path that removes.
  Guard one: task 2.2 adds `require_path_segment <flag> <value>`, rejecting empty, `/`, `.`, `..` and a leading `-`. Task 2.2 wires it into the validation block at `scripts/install.sh:412-414`. That block sits inside `main` before transport selection, so `--bfs-service`, `--bucket` and `--slc-name` pass it on every invocation. Those three globals are settable only through those three flags (`scripts/install.sh:397-399`), so no bypass exists.
  Guard two: task 2.5 refuses any destination whose physically resolved parent does not equal the physically resolved bucket directory. The comparison is real, not a string prefix: task 2.3 spells out `cd … && pwd -P` or `realpath` for the bucket directory, and task 2.5 repeats "physically resolved" for both sides of the parent comparison. `--slc-name ../../..` now yields a resolved parent of the bucket directory's grandparent, which is unequal, so the destructive step never runs. Task 2.4's test drives that refusal directly, which matters because the harness sources `install.sh` and calls functions in-process without ever running `main` (`scripts/tests/install-personal-test.sh:20`).
  The rejection list is sufficient for this destination. A shell variable cannot carry a null byte, so no null-byte case exists. A symbolic link is reachable only as the final component, and `rm -rf` on a symbolic link removes the link rather than its target. A glob character survives `require_path_segment` but is inert inside the quoted join the existing code already uses (`scripts/install.sh:380`).
  Residual, non-blocking: `--slc-name udf` still removes the operator's own `udf/` directory, because that is the documented meaning of the flag and the SSH mechanism behaves the same way today (`scripts/install.sh:384`). plan.md § Impact states "an operator's own `udf/*.so` artifacts in the same bucket survive the install", which holds for every value except that one collision. See the Task Breakdown finding on task 4.1.

- **Resolved: [COMPLETENESS_GAP] "Removes it" read as removing the whole bucket directory.**
  The fix is in the task text, not only in the summary. Task 2.5 reads "Resolve the bucket directory through `deployment_bucketfs_dir`, then join `<slc-name>` to it to form the destination", then "Print the joined destination, then remove only it", then "Never remove or recreate the bucket directory itself, which also holds the operator's own `udf/*.so` files". No reading of that text removes the bucket directory.
  The spec clause is testable and tested. `container/personal-install-local` § "The shared-directory mechanism extracts into the deployment's own BucketFS directory" carries "*AND* it MUST leave every file under that host directory outside `<slc-name>/` untouched". Task 2.4's test seeds `udf/libother.so` beside `<slc-name>/`, extracts twice, and asserts that file is still present after both extractions. That assertion fails against a whole-bucket removal and passes against the specified one, so it discriminates. The live deployment carries exactly that file (`notes/planning.md:92`), so the fixture matches the real layout.

- **Not resolved: [REQUIREMENT_CONFLICT] One generic message for two different shared-directory failures.**
  The two messages are distinguishable and the exit-status contract is documented, but the contract now mislabels a third case that the plan itself requires. See the BLOCKER under Requirement Quality. No other caller is affected: `extract_slc_into_shared_bucketfs` (task 2.5) is the only other reader of `deployment_bucketfs_dir`, and it treats any non-zero status as a failure, so the split from zero-versus-non-zero costs it nothing.

## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 2.5; § Dependencies
- Issue: carried forward from round 3, not applied and not recorded as a decision. The SSH mechanism extracts inside the VM with the VM's GNU `tar` (`scripts/install.sh:384`). The shared-directory mechanism extracts with the invoking host's `tar`, which on the documented macOS workstation is bsdtar. The only post-extraction check task 2.5 specifies is "confirm `exaudf/exaudfclient` is executable". `container/slim-image` § "SLC tarball ships the /conf resolver symlinks" requires `etc/hosts` and `etc/resolv.conf` to be symbolic links into `/conf/` for DNS to work. A host `tar` that drops or rewrites those links leaves an SLC that passes the specified check and fails at run time.
- Fix: Extend task 2.5 in plan.md to require `extract_slc_into_shared_bucketfs` to confirm that `etc/hosts` and `etc/resolv.conf` are symbolic links after extraction. Extend task 2.4's fixture tarball to carry one symbolic link and assert it survives. Add one sentence to plan.md § Dependencies naming the host `tar` implementations the mechanism is verified against.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Implementation Tasks 3.3 against § Implementation Tasks 2.3; `container/personal-install-local` § "The shared-directory destination is checked before anything is removed"
- Issue: the round-3 fix split `deployment_bucketfs_dir`'s failures into two exit statuses, but status 1 carries four causes while task 3.3 reports it as one. Task 2.3 lists the causes: "Fail with a clear error when no line matches, when the file is absent, when the joined path is not an existing directory, or when it is not inside `<dir>`", then "Return exit status 2 when the mapping file itself is absent and 1 for every other failure". Task 2.3's own rationale already overstates the result: "so a caller can tell 'this deployment publishes no mapping' from 'this pair is not served'". Task 3.3 turns that overstatement into the operator-facing message: "Any other failure means the deployment does publish a mapping and the requested pair is wrong, so it fails naming that service and bucket pair and the pairs the mapping does serve." The missing-directory cause is not hypothetical. `container/personal-install-local` requires it: "*AND* it MUST fail when the host directory that mapping resolves to does not already exist, because the deployment creates that directory and the install only adds the SLC under it". `notes/planning.md:111` records "Whether `bucketfs.conf` exists before a deployment's first start" as unverified, so the state where the mapping line exists and its host directory does not is reachable. The operator then reads that `bfsdefault`/`default` is not served, followed by a list of served pairs containing `bfsdefault`/`default`. That is the same defect round-3 BLOCKER 3 fixed, moved one case along. Task 2.1's test list asserts only "a failure" for each of the four causes and never asserts the status values, so no test pins the contract at its own level.
- Fix: In plan.md task 2.3, give `deployment_bucketfs_dir` three exit statuses and state each one's single cause: 2 when the mapping file is absent, 3 when the mapping file names no line for the requested pair, and 1 for every other failure (the resolved host directory is absent, or it resolves outside `<dir>`). In plan.md task 3.3, branch on all three: status 2 fails naming both mechanisms' prerequisites, status 3 fails naming the requested pair and the pairs the mapping does serve, and status 1 fails naming the resolved host directory and the reason it is unusable, without claiming the flags are wrong. Add to task 2.1's `resolves_shared_bucketfs_dir_from_mapping` test list an assertion of the exit status returned for each of the four failure fixtures. Add one clause to the `container/personal-install-local` scenario "The deployment directory selects the local install mechanism": "*AND* when the mapping names the requested pair but the host directory it resolves is unusable, it MUST fail naming that directory rather than the requested pair, because the flags are correct".

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: plan.md § Implementation Tasks 2.3; `container/personal-install-local` § Background, paragraph 3
- Issue: carried forward from round 3, not applied. Both artifacts say "the VM-side path that line names", singular. A live mapping line names two paths: `/exa/bucketfs/bfsdefault/default bfsdefault default /buckets/bfsdefault/default - P` (`notes/planning.md:91`). Field 1 is the VM-side directory that joins to `vm-shared`. Field 4 is the bucket path the engine serves. The `__builtin__` line publishes a field 4 of `/exa/slc`, which is not a `/buckets/…` path, so the two fields are not interchangeable. Task 2.1's expected-value assertion catches a field-4 implementation, so the failure mode is a wasted implementation cycle rather than a shipped defect.
- Fix: In plan.md task 2.3, replace "the VM-side path that line names" with "the line's first whitespace-separated field, the VM-side directory that backs the bucket, matched on fields 2 and 3". Add a failure condition: the function fails when the line's fourth field is not `/buckets/<service>/<bucket>`, because `script_languages_entry` assumes that path. Mirror both changes in the `container/personal-install-local` Background paragraph 3 and add the field-4 mismatch case to task 2.1's test list.
