# Feature: cargo-exaudf

Provides the `cargo exasol-udf` developer CLI that scaffolds a Rust UDF crate and builds it into a glibc-dynamic cdylib `.so` — so authors never hand-manage the build target or ABI constants.

## Background

`cargo-exasol-udf` is a Cargo subcommand binary invoked as `cargo exasol-udf <subcommand>`. By default `build` runs a plain host `cargo build --release`, producing a glibc-dynamic cdylib at `target/release/lib<crate>.so`; an optional `--target <triple>` flag overrides the build target for a native build on that host. The CLI performs no network I/O. The scaffold generated by `new` models the scalar RETURNS value-return channel.

ABI and dlopen-platform validation of a built `.so` — checking it against `EXA_UDF_ABI_VERSION`/`EXA_SDK_FINGERPRINT` and against the SLC's glibc floor and library surface — is the `validate` subcommand, specified separately in `tools/cargo-exaudf-validate`.

### Scenario: new scaffolds a buildable UDF crate

* *GIVEN* a target directory that does not yet contain a crate
* *WHEN* the author runs `cargo exasol-udf new my-udf`
* *THEN* the CLI MUST create a `Cargo.toml` with `crate-type = ["cdylib"]` and dependencies on `exasol-udf-sdk` and `exasol-udf-macros` whose version pins track the current SDK major.minor line
* *AND* it MUST create a `src/lib.rs` containing a `#[exasol_udf]` entry point that models the scalar RETURNS channel, returning `Result<Option<i64>, UdfError>` with a placeholder `Ok(None)` body
* *AND* the generated crate MUST compile as written against that SDK, the macro deriving the RETURNS output shape from the `Option<i64>` return type
* *AND* the generated `[profile.release]` MUST set `lto = "fat"` and `codegen-units = 1` alongside `strip = true`, so a scaffolded UDF inlines across the SDK crate boundary by default instead of paying a cross-crate call per cell in the hot emit loop
* *AND* it MUST NOT set `panic = "abort"`, because the macro-generated run shim converts a UDF panic into an error code through `catch_unwind` and needs unwinding
