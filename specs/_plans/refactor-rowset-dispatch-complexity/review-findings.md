# Code Review Findings: refactor-rowset-dispatch-complexity

## Summary
- Files reviewed: 11
- Total findings: 8 (standard: 6, expert: 2)

Independently verified before reviewing: `cargo fmt --check` clean, `cargo clippy --all-targets --all-features -- -D warnings` exit 0, `cargo test -p exa-udf-runtime --all-features` all suites green (22 dispatch, 17 single_call, lib + arrow suites), dispatch suite wall clock 0.68 s. The behavior-preserving claim holds where checked: `run_group`'s decomposition preserves the original `run_err` → `exit.take()` → tail-flush ordering exactly, `fixed_cell_cost` returns `Some` for precisely the seven `DataType` arms the old per-arm loops covered, and `accumulate_costs`' null predicate is the same expression the old arms used. The emit invariants are intact and now pinned harder than before: `EMIT_BUFFER_LIMIT_BYTES` is still the literal `4_000_000` (`rowset.rs:142`), `tail_flush` still fires on any non-empty buffer regardless of threshold (`dispatch.rs:248`), and `emit_buffer_flushes_mid_group_before_tail_flush` pins the crossing at exactly 500,000 × 8 bytes with a separate tail flush.

Two things the brief asked about were assessed and deliberately **not** raised as findings:

- **`rowset.rs` as a dumping ground.** The concern is real but predates this plan and this change did not worsen it: the file went 2020 → 1929 lines (net −91), and the two new macros sit adjacent to their only two consumers (`HostContextBridge`, `SingleCallContext`), both of which already lived here. Extracting them plus `HandshakeMeta`/`SingleCallContext`/the connect-back helpers into a `context.rs` would require relocating ~1500 lines of `rowset_tests.rs` alongside them and `#[macro_export]`-ing crate-internal macros — a large, risky churn with no defect behind it. Leave as is.
- **The `single-call-fixture` sentinel arguments (`"SUCCEED"`, `"CONNECTION_PROBE"`).** Legitimate test-fixture design, not production contortion. The crate is test-only by its own module doc, the vtable exposes exactly one slot per hook so the branches cannot be split into separate functions, and the same idiom already governed the fixture's pre-existing deliberate-failure path. Do not remove them.

### crates/exa-udf-runtime/src/rowset_tests.rs

## Expert fixes

### crates/exa-udf-runtime/src/rowset.rs

#### [TACTICAL_SHORTCUT] `accessor_value` silently rewrites every pre-epoch nanosecond timestamp to the Unix epoch, and the change pins it as intended
- Location: line 687
- Issue: the `TsNanosecond` arm computes `chrono::DateTime::from_timestamp(ns / 1_000_000_000, (ns % 1_000_000_000) as u32)` (line 690). For any negative `ns`, Rust's truncating `%` yields a negative remainder that wraps when cast to `u32` (for `ns = -1`: `4_294_967_295`), `from_timestamp` rejects it because it requires nsecs < 2_000_000_000, and `unwrap_or_default()` swallows the failure and returns the Unix epoch. Every pre-epoch nanosecond-unit Arrow timestamp a UDF emits therefore reaches the DB as `1970-01-01 00:00:00.000000000` with no error anywhere — silent data corruption on both the `encode_slice` and `arrow_batch_to_value_rows` paths. This change made `accessor_value` the single owner of that decision, so the arithmetic now exists in exactly one place and the fix is one line; instead, `accessor_value_timestamp_nanosecond_negative_degrades_to_epoch` (rowset_tests.rs:3019) was added to assert the corrupted output as correct, with its doc comment declaring the real fix "out of scope" and no GitHub issue filed against it. That is a shortcut with no scheduled follow-up, and it now has a green test defending it against the very fix it describes.
- Fix: In crates/exa-udf-runtime/src/rowset.rs, change `accessor_value`'s `TsNanosecond` arm to use `ns.div_euclid(1_000_000_000)` and `ns.rem_euclid(1_000_000_000) as u32` so a negative `ns` yields a non-negative nanosecond remainder and the correct second. Then in crates/exa-udf-runtime/src/rowset_tests.rs rename `accessor_value_timestamp_nanosecond_negative_degrades_to_epoch` to `accessor_value_timestamp_nanosecond_negative_yields_pre_epoch_instant`, rewrite its doc comment to state the euclidean-division contract instead of the degradation, and assert `ns = -1` yields `1969-12-31 23:59:59.999999999`; add a second case for a whole-second-aligned negative value (`ns = -1_000_000_000` → `1969-12-31 23:59:59`). Verify `push_batch_equals_row_push`, `push_batch_byte_estimate_parity`, `fast_path_to_proto_byte_identical_to_row_path` and `encode_slice_matches_row_path_across_every_block_type` all stay green afterwards — both batch paths share `accessor_value`, so their byte-identity with each other is unaffected by the correction.

### crates/exa-udf-runtime/src/wire.rs

#### [MISSING_BOUNDARY_TEST] The ping-retry path is tested for one ping only, and recurses without bound beyond it
- Location: line 24
- Issue: `wire::request` answers a mid-exchange ping by calling itself (`return request(transport, proto, proto.ping_reply(&s));`). If the DB answers the ping reply with another ping the function recurses again, with no bound and no tail-call guarantee from rustc — N consecutive pings cost N stack frames on the crate's single shared wire path, now used by both dispatchers plus the emit flusher and batch fetcher. The doc comment (line 13) describes this as "retrying the same request once", which understates its own contract: it retries once per ping, unboundedly. The new `ping_pong_mid_exchange_retries_transparently` (tests/dispatch.rs:838) drives exactly one ping, so the recursive case — the only one the recursion exists for — has no coverage in either dispatcher. This is squarely in scope: the plan's stated purpose for `wire.rs` is to be the one owner of the ping-retry decision.
- Fix: In crates/exa-udf-runtime/src/wire.rs, rewrite `request` as a loop instead of a recursion — take `req` into a local `let mut req = req;`, then `loop { transport.send(&req)?; let resp = transport.recv()?; let (event, action) = proto.step(resp)?; match action { Some(HostAction::PingReply(s)) => req = proto.ping_reply(&s), _ => return Ok(event) } }` — which is behavior-identical (`ping_reply` takes `&self`) and grows no stack. Correct the doc comment to say the exchange answers every ping in a row transparently, not "once". Then in crates/exa-udf-runtime/tests/dispatch.rs extend `ping_pong_mid_exchange_retries_transparently` (or add a sibling test) so the mock DB answers the first `MT_RUN` with `MT_PING_PONG`, answers the client's ping echo with a *second* `MT_PING_PONG` carrying a different `meta_info`, asserts the client echoes that second token too, and only then answers with `MT_CLEANUP` — proving consecutive pings stay transparent.
