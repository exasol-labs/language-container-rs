## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Requirements row 3; § Implementation Tasks 3.6 and 3.7; `protocol/handshake/spec.md:57`
- Issue: two users execute the same script through the same schema, and the plan gives them different privilege sets. Task 3.6 grants `IT_VIEW_OWNER` both `USAGE ON SCHEMA IT_RUST` and `EXECUTE ON SCRIPT IT_RUST.CURRENT_USER_META`. Task 3.7 grants `IT_IMPERSONATED` only `EXECUTE ON SCRIPT IT_RUST.CURRENT_USER_META`, and the impersonated session then selects that script under a user who "loses all their current privileges". `details_rights_management.htm` states the rule for both cases: "For all objects, the `USE ANY SCHEMA` system privilege or `USAGE` object privilege is required on the schema of the object in addition to the other privileges." The asymmetry is harmless only because of an unstated default: `privileges.htm` states "By default, all users get the `USE ANY SCHEMA` system privilege because they are granted to `PUBLIC` role." That default carries the impersonated read today, and it also makes § Requirements row 3's `MUST` on `IT_VIEW_OWNER` a belt-and-braces grant rather than the necessity the row claims. A container or cluster with `USE ANY SCHEMA` revoked from `PUBLIC` fails the IMPERSONATE scenario on a privilege error and passes the view-owner scenario, with no plan text to explain the difference.
- Fix: Add `GRANT USAGE ON IT_RUST TO IT_IMPERSONATED` to task 3.7's statement list, immediately after its `GRANT EXECUTE ON SCRIPT` line, so both non-DBA users hold the same schema privilege. Extend `plan.md` § Requirements row 3 with the `PUBLIC` default and its citation: `USE ANY SCHEMA` reaches every user through `PUBLIC` by default, so both grants are explicit rather than load-bearing on the default Docker container. Source: https://docs.exasol.com/db/latest/database_concepts/privileges.htm

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Design/Architecture line 45; § Implementation Tasks 3.7; § Requirements row 2; `decision-log.md` § Design Decisions [3] and [4]
- Issue: the plan calls the revert a safeguard and then makes it a hard failure point. `plan.md:45` states "The revert is a second safeguard, not the mechanism the design depends on". Task 3.7 nevertheless issues `GRANT IMPERSONATION ON SYS TO IT_IMPERSONATED` unconditionally and asserts `current_user` reports `SYS` after `IMPERSONATE SYS`. Whether Exasol accepts an `IMPERSONATION` grant whose target is `SYS` is unverified: `sql/impersonate.htm` names `IMPERSONATE ANY USER` or `IMPERSONATION ON <user/role>` as the requirement and states no restriction on privileged targets, and its examples use `other_user`, `TECHNICAL_DBA`, and `[TableauServerUser]`. A rejection at either statement fails the plan's primary scenario for a reason unrelated to the identity fields under test, and the failure lands after the two cross-checks that the scenario exists to produce.
- Fix: State the assumption in `plan.md` § Requirements row 2: Exasol documents no restriction on `IMPERSONATION` grants whose target is `SYS`, and the acceptance of `GRANT IMPERSONATION ON SYS TO IT_IMPERSONATED` is unverified until the live run. Add to task 3.7 that the restore is non-fatal: run the grant, the `IMPERSONATE SYS`, and the post-revert assertion inside a branch that records the database's response in a code comment and continues to the connection close if the database rejects either statement, because the close already carries the design's correctness.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `plan.md` § Implementation Tasks 3.6 and 3.7
- Issue: both tasks spell out full SQL for every other statement and abbreviate the two `CREATE USER` statements to `CREATE USER IT_VIEW_OWNER` and `CREATE USER IT_IMPERSONATED`. Exasol requires an authentication clause: `create_user.htm` ships `CREATE USER user_1 IDENTIFIED BY "h12_Xhz";` and states "Users can authenticate against the database with a password or through Kerberos, OpenID, or LDAP." A bare `CREATE USER` is a syntax error. Task 3.7 drops its user with `DROP USER IT_IMPERSONATED CASCADE` while task 3.6 says only "drop the view, the schema, and the user", so the two cleanups disagree on the form.
- Fix: Write both statements in full in tasks 3.6 and 3.7 as `CREATE USER <name> IDENTIFIED BY "<literal>"`, and cite https://docs.exasol.com/db/latest/sql/create_user.htm in `plan.md` § Requirements row 1. Change task 3.6's cleanup to the explicit sequence `DROP VIEW IT_VIEW_SCOPE.V_CURRENT_USER_META`, `DROP SCHEMA IT_VIEW_SCOPE CASCADE`, `DROP USER IT_VIEW_OWNER CASCADE`, matching task 3.7's form.
