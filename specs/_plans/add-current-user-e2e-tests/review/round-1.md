## Premortem

Three failure stories, written before scoring.

1. **The spec library records a false database fact.** `specs/protocol/handshake` ships the requirement "after `IMPERSONATE`, `current_user` MUST report the impersonated user". The live database reports the logged-in user instead. During implementation the assertion was relaxed to make CI green, the spec text stayed, and issue #92's original prediction was recorded as refuted. Routes to `[INTENT_DRIFT]`, `[UNSTATED_ASSUMPTION]`.
2. **The integration job goes red and nobody can localise the fault.** The single side connection is impersonated by the second scenario, so every later side scenario fails on a privilege error, or fails because task 3.5 already closed the connection. The failure mode looks identical to a broken identity field. Routes to `[REQUIREMENT_CONFLICT]`, `[HIDDEN_DEPENDENCY]`.
3. **The only differential `scope_user` coverage is deleted as flaky.** The view owner was never granted `EXECUTE` on the script, so the view fails at query time inside a UDF. The cheapest fix is to drop the scenario, which leaves `scope_user` with no test that distinguishes it from `current_user`. Routes to `[HIDDEN_DEPENDENCY]`.

## Intent Fidelity

The added fifth scenario is certified as a faithful, minimal correction, not scope creep: `getScopeUser()`'s documented definition names the view-owner case as the one configuration where `scope_user` diverges from `current_user`, so without it the plan proves only that the two fields are equal. The 20-of-22 migration is certified against the interview answer: the interview said "all 15+ existing call sites", the survey returned 22, 20 migrate, and the two exceptions are blocked by a Cargo feature-resolution constraint rather than dropped. The count went up, not down.

#### [INTENT_DRIFT] BLOCKER
- Location: `decision-log.md` § Design Decisions [1]; `plan.md` § Design/Context line 13 and § Consequences row 1; `protocol/handshake/spec.md` § Scenario "IMPERSONATE redirects the reported current user within the session"
- Issue: the plan overrides the user's verbatim issue text on a citation that does not support the override, then records the opposite as a normative `MUST`. Decision [1] states the issue's prediction "contradicts primary Exasol documentation and would fail against every Exasol version". Verification refutes that: the `getScopeUser()` quote is accurate, and the "loses all their current privileges" quote is accurate, but **no Exasol page states what `CURRENT_USER` or the UDF `current_user` field reports after `IMPERSONATE`**. The docs instead establish a two-user model that makes the issue's reading plausible: `exa_dba_sessions.htm` documents `USER_NAME` as "Name of the logged-in user" and `EFFECTIVE_USER` as "Effective user of the session (changeable via IMPERSONATE)". The privilege-replacement quote is about privileges, not about which user the metadata field names. What the documentation **does** refute is only the issue's *split* claim: outside a view, `scope_user` equals `current_user` by definition, so the two fields cannot diverge under plain `IMPERSONATE`. The plan asserts the undocumented half as fact (`current_user` MUST report `IT_IMPERSONATED`), which violates CLAUDE.md's "Do not claim project behavior without evidence" and risks recording a false database fact into the permanent spec library.
- Fix: Split the claim in three artifacts. In `protocol/handshake/spec.md`, rewrite the IMPERSONATE scenario so the documented invariant is the `MUST` and the undocumented direction is discovered: keep "`scope_user` MUST equal `current_user`, because no view wraps the call" and "`script_schema` MUST stay unchanged"; replace "`current_user` MUST report `IT_IMPERSONATED`" with a step requiring the reported `current_user` to equal the value that `SELECT CURRENT_USER` returns in the same impersonated session, and a step requiring it to equal exactly one of `EXA_DBA_SESSIONS.USER_NAME` or `EXA_DBA_SESSIONS.EFFECTIVE_USER` read for that session, so the scenario establishes the mapping instead of presupposing it. Add the corresponding cross-check reads to task 3.5. In `decision-log.md` entry [1], delete the claim that the issue's prediction "would fail against every Exasol version", and state instead that Exasol documents no mapping from `IMPERSONATE` to `CURRENT_USER`, that the `getScopeUser()` definition refutes only the field *split*, and that the scenario therefore records the observed mapping. In `plan.md` line 13 and the § Consequences row, replace "Both fields therefore move together under `IMPERSONATE`" with the documented invariant (the two fields cannot diverge without a view) and state the mapping as unverified until the live run.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Design/Architecture lines 37-39 and § Patterns row 1; `decision-log.md` § Design Decisions [3]
- Issue: decision [3]'s load-bearing premise is refuted by the page the plan itself cites. `plan.md` line 37 states "`IMPERSONATE` has no withdraw statement, so an impersonated session cannot be reliably returned to `SYS`", and decision [3] concludes "Closing a connection is the only reliable way to undo an impersonation." `sql/impersonate.htm` states: "There is no statement for withdrawing an impersonation. **To revert to the user that initiated the session, the user must impersonate again as the original user.**" A documented revert path exists (`IMPERSONATE SYS`), it needs one extra grant issued before the first impersonation, and every downstream design consequence in the plan rests on the false premise.
- Fix: Add the revert path to `plan.md` § Requirements as a new row: the scenario MUST run `GRANT IMPERSONATION ON SYS TO IT_IMPERSONATED` before the first `IMPERSONATE`, so the session can return with `IMPERSONATE SYS`, citing `https://docs.exasol.com/db/latest/sql/impersonate.htm`. Rewrite `decision-log.md` entry [3]'s Rationale and Alternatives to drop "Closing a connection is the only reliable way to undo an impersonation" and re-justify the side connection on the surviving ground alone: a mid-scenario failure leaves the shared session in an unknown user identity, and the shared session carries roughly 30 later scenarios. Add the `IMPERSONATE SYS` restore step to task 3.5 and to the `plan.md` § Patterns row 1 rationale.

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `plan.md` § Implementation Tasks 3.7; `protocol/handshake/spec.md` § Scenario "scope_user reports the view owner when the script runs inside a view"
- Issue: the view-owner scenario grants the view owner nothing, so it cannot pass. Task 3.7 reads "create `IT_VIEW_OWNER`, create `IT_VIEW_SCOPE`, move its ownership to that user, create the wrapping view, select from it as `SYS`, then drop the view, schema, and user." `details_rights_management.htm` states for `SELECT * FROM v;`: "The owner of v must possess the privileges required to run the underlying query in v." The underlying query calls `IT_RUST.CURRENT_USER_META`, so `IT_VIEW_OWNER` needs `EXECUTE` on that script and access to schema `IT_RUST`. Task 3.5 grants exactly that for its impersonated user; task 3.7 lists no grant at all. Separately, task 3.7's ordering is the undocumented one: it changes the schema owner *before* creating the view. `sql/alter_schema.htm` documents `CHANGE OWNER` as re-owning "the schema and all its objects", but no page documents the owner of a view that `SYS` creates in a schema already owned by another user, and `exa_all_views.htm` carries an independent `VIEW_OWNER` column, so the shortcut is not safe.
- Fix: In task 3.7, add `GRANT EXECUTE ON SCRIPT IT_RUST.CURRENT_USER_META TO IT_VIEW_OWNER` and a schema-access grant on `IT_RUST` to `IT_VIEW_OWNER`, and reorder the statements to create the view first and then run `ALTER SCHEMA IT_VIEW_SCOPE CHANGE OWNER IT_VIEW_OWNER`, so the documented re-own path sets the view owner. Add both grants to the scenario's `GIVEN` in `protocol/handshake/spec.md`. Replace task 3.7's `FROM`-less fallback hedge with the citation that settles it: `functions/alphabeticallistfunctions/scope_user.htm` ships `CREATE VIEW scope_view AS SELECT SCOPE_USER;` as an official example, so keep the one-row-source wrapper as a stated fallback only, not as an open question.

## Design Depth

The `test_support` module is certified deep and its two-type split is certified correct against the codebase. `crates/exasol-udf-sdk/src/context_tests.rs:84-138` holds five tests that assert `UdfContext` provided-method default bodies through `DummyCtx`, so decision [6]'s shadowing hazard is real and `DefaultsCtx` is the right answer. Decision [9]'s refusal of an out-of-range-error knob is certified: the surveyed doubles disagree (`UdfError::Type("out of range")` in `context_tests.rs:39`, `UdfError::User(format!("col {} out of range", col))` in `test-udfs/set-sum/src/lib.rs`) and no test asserts either, so the knob would leak an accidental difference. Dependency direction is certified: `test_support` names only `UdfContext`, `Value`, and `UdfError`.
