# Feature: cargo-exaudf

Provides the `cargo exasol-udf` developer CLI that scaffolds a Rust UDF crate and builds it into a glibc-dynamic cdylib `.so` — so authors never hand-manage the build target or ABI constants.

## Background

`cargo-exasol-udf` is a Cargo subcommand binary invoked as `cargo exasol-udf <subcommand>`. By default `build` runs a plain host `cargo build --release`, producing a glibc-dynamic cdylib at `target/release/lib<crate>.so`; an optional `--target <triple>` flag overrides the build target for a native build on that host. The CLI performs no network I/O. The scaffold generated by `new` models the scalar RETURNS value-return channel.

ABI and dlopen-platform validation of a built `.so` — checking it against `EXA_UDF_ABI_VERSION`/`EXA_SDK_FINGERPRINT` and against the SLC's glibc floor and library surface — is the `validate` subcommand, specified separately in `tools/cargo-exaudf-validate`.

## Scenarios

### Scenario: new scaffolds a buildable UDF crate

* *GIVEN* a target directory that does not yet contain a crate
* *WHEN* the author runs `cargo exasol-udf new my-udf`
* *THEN* the CLI MUST create a `Cargo.toml` with `crate-type = ["cdylib"]` and dependencies on `exasol-udf-sdk` and `exasol-udf-macros` whose version pins track the current SDK major.minor line
* *AND* it MUST create a `src/lib.rs` containing a `#[exasol_udf]` entry point that models the scalar RETURNS channel, returning `Result<Option<i64>, UdfError>` with a placeholder `Ok(None)` body
* *AND* the generated crate MUST compile as written against that SDK, the macro deriving the RETURNS output shape from the `Option<i64>` return type

### Scenario: new rejects an existing non-empty target

* *GIVEN* a target directory that already contains a `Cargo.toml`
* *WHEN* the author runs `cargo exasol-udf new` against that directory
* *THEN* the CLI MUST refuse to overwrite and exit with a non-zero status
* *AND* it MUST print a message naming the conflicting path

### Scenario: build produces a loadable host cdylib

* *GIVEN* a UDF crate produced by `cargo exasol-udf new`
* *WHEN* the author runs `cargo exasol-udf build` with no `--target` flag
* *THEN* the CLI MUST invoke `cargo build --release` for the host target, passing no `--target`
* *AND* it MUST print the path `target/release/lib<crate>.so`
* *AND* the produced `.so` MUST be a cdylib that exports at least one `__exa_udf_entry_<NAME>` symbol

### Scenario: build honors an explicit target override

* *GIVEN* a UDF crate and a host whose toolchain has the target triple `<triple>` installed
* *WHEN* the author runs `cargo exasol-udf build --target <triple>`
* *THEN* the CLI MUST invoke `cargo build --release --target <triple>`
* *AND* it MUST print the path `target/<triple>/release/lib<crate>.so`

### Scenario: build emits a schema sidecar for annotated UDFs

* *GIVEN* a UDF crate whose struct is annotated `#[exasol_udf(input(...), emits(...))]`
* *WHEN* the author runs `cargo exasol-udf build`
* *THEN* the CLI MUST write a `<crate>.udf-meta.json` sidecar next to the `.so` describing the input and emit columns
* *AND* a bare `#[exasol_udf]` crate MUST build without producing a sidecar

### Scenario: build verifies the artifact exports at least one named entry point

* *GIVEN* an author crate annotated with `#[exasol_udf]`
* *WHEN* the author runs `cargo exasol-udf build`
* *THEN* after producing the `.so` the CLI MUST verify the artifact exports at least one `__exa_udf_entry_<NAME>` symbol resolving to a non-null vtable
* *AND* a build whose artifact exports no named entry point MUST fail with a clear error rather than producing a silently-unusable `.so`
